Wenn die Felder für deine Fahrzeugdetails vor 6.1.2 konfiguriert wurden, konnte das Hinzufügen von Galeriebildern mit anschließendem Klick auf „Aktualisieren“ die gerade hinzugefügte Galerie löschen. 6.1.3 behebt das, und du musst dafür nichts tun: keine Datenbankänderung, kein erneutes Speichern der Einstellungen. Die Installation genügt.

<!--truncate-->

## Die Galerie verschwindet nicht mehr

Zwei Felder, die nie echte Felder waren – ein leeres **Bild** und ein leeres **Galeriebilder** –, standen auf jedem Fahrzeugbildschirm im Raster der Fahrzeugdetails. Sie wirkten rein kosmetisch. Das waren sie nicht: Das zweite trug denselben Formularfeldnamen wie die Galerie selbst, und wenn zwei Felder auf einer Seite denselben Namen haben, sendet der Browser beide, und das letzte gewinnt. Das leere Feld kam zuletzt, sodass „Aktualisieren“ die gerade hochgeladene Galerie mit nichts überschrieb.

6.1.2 hat verhindert, dass neue Websites jemals in diesen Zustand geraten, aber nichts für Websites getan, die sich bereits darin befanden – und das sind die meisten Websites, die ihre Fahrzeugeinstellungen mindestens einmal gespeichert hatten. Warum das Problem bestehen blieb, ist einen Satz wert: Der Code, der festlegt, welche Felder existieren, erfand für jeden Namen, den er nicht kannte, eine Bezeichnung, und eine erfundene Bezeichnung ließ einen unbekannten Namen für jede nachfolgende Prüfung wie ein echtes Feld aussehen. Jetzt verwirft er, was er nicht kennt.

Wenn deine Website betroffen ist, ist das Update also die komplette Lösung. Der übrig gebliebene Eintrag bleibt in deinen Einstellungen und wird ab sofort einfach ignoriert.

**Eine Sache solltest du wissen.** Wenn du unter *Namen bearbeiten* den Namen eines benutzerdefinierten Details leerst, verschwindet dieses Detail jetzt aus dem Raster, statt unter einem aus seinem internen Schlüssel generierten Namen angezeigt zu werden. Nichts wird gelöscht – sobald du wieder einen Namen eingibst, ist es sofort zurück –, und die öffentliche Seite deiner Website hat ein solches Feld bereits ausgeblendet, sodass beide jetzt übereinstimmen.

## Das Speichern einer normalen Seite schreibt keine Buchungsdaten mehr darauf

Ein Handler, der Buchungsinformationen speichert, reagierte auf jeden Speichervorgang auf der Website statt nur auf Buchungen. Das Speichern einer nicht zugehörigen Seite oder eines Beitrags konnte daher einen Buchungsstatus darauf schreiben. Niemand konnte auf Daten zugreifen, auf die er keinen Zugriff haben durfte – die vorhandene Prüfung fragte weiterhin, ob du diese Seite bearbeiten darfst –, aber das Plugin schrieb seine eigenen Felder auf Objekte, die es nichts angingen.

Fünfzehn Handler für Fahrzeuge und Buchungen prüfen jetzt vor dem Schreiben, in welche Art von Beitrag sie schreiben. Einer davon war ein aktiver Pfad, der Daten zur Fahrzeugsortierung an jeden Beitrag anhängen konnte, auf den er gerichtet wurde.

## Ein Admin-Bildschirm, der fehlschlägt, sagt das jetzt auch

Wenn die Daten eines Bildschirms nicht geladen werden konnten, zeigten manche Bildschirme eine kurze Meldung „Etwas ist schiefgelaufen, bitte aktualisieren“, während andere einfach leer blieben – eine weiße Fläche unter dem WordPress-Menü ohne jede Erklärung. Jetzt zeigt jeder Bildschirm die Meldung an, und eine Prüfung verhindert, dass neue Bildschirme ohne sie ausgeliefert werden.

## Unter der Haube

Gemeinsam genutzte Admin-Bausteine werden jetzt aus einem gemeinsamen Paket geladen, statt als Kopien innerhalb von Rentiva vorgehalten zu werden, und doppelte Stildeklarationen wurden zusammengeführt. Das wurde mit einem Vorher-Nachher-Vergleich im hellen und im dunklen Modus überprüft: Auf deiner Website wird nichts anders dargestellt.
